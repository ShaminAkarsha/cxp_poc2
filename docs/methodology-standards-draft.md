# Draft: methodology — completing and hardening an incomplete specification

*Draft text for the report's methodology section. Figures are taken from `docs/standards-traceability.json` (45 entries, 2026-10-13). Section numbers are deliberately omitted here; cite them from the traceability table once every entry marked "section to verify" has been checked.*

Because the Credential Exchange Protocol is a Working Draft, a faithful implementation could not be derived from the specification text alone. Every point at which CXP or CXF was silent, internally inconsistent or referred to material that no longer exists was therefore recorded in a gap register before it was implemented, and each resolution was traced to its source in a machine-checked traceability record. Seventeen such points had to be resolved for the protocol to operate at all; these completion choices are identical in both conformance profiles. Wherever possible they were resolved by adopting the standard that the specification itself points towards or that governs the underlying mechanism: Hybrid Public Key Encryption (RFC 9180) for the key encapsulation, key schedule and secret export; JSON Web Encryption and JSON Web Algorithms (RFC 7516, RFC 7518) for the per-file containers; JSON Web Key (RFC 7517, RFC 8037) for public-key encoding; RFC 4648 and the JOSE base64url convention (RFC 7515) for binary values; RFC 8259 and I-JSON (RFC 7493) for JSON processing; and the ZIP application note with DEFLATE (RFC 1951) for the archive. Where no external standard applied, as with the naming of exchange files or the interpretation of an editorial defect in the direct response mode, the choice was recorded explicitly as a design decision together with its justification, so that no behaviour of the implementation rests on an unstated assumption.

The hardened profile closes the security-relevant gaps by means of twenty-one policy flags, each of which corresponds to exactly one gap; the correspondence is enforced by automated tests. The controls draw predominantly on IETF specifications, which account for 62 of the 89 citations in the record: the HPKE `info` parameter and authenticated mode (RFC 9180), canonical JSON (RFC 8785) and JWK thumbprints (RFC 7638) bind each response to the exact request and allow the user to confirm keys, while TLS 1.3 (RFC 8446) with an X.509 profile following RFC 5280 protects the direct channel. NIST publications (SHA-256 under FIPS 180-4, AES-GCM under SP 800-38D, and the guidance of SP 800-63B-4, SP 800-57 and SP 800-88) and OWASP guidance on transaction authorisation, file upload and transport-layer security inform the remaining controls, including consent, freshness, decompression limits and key-material handling. Two gaps are closed indirectly by controls introduced for other gaps. Five remain open. Three cannot be closed conformantly without a change to the specification (the mandatory zero signature counter, the reuse of PRF seeds across importers, and the absence of backup-state fields in CXF), and one, the retention of the source credential, lies outside the protocol's stated scope; these are reported as residual risks and as recommendations for future revisions of CXP and CXF. The fifth, notifying the user of passkeys excluded from an export, is recommended by CXF but was not implemented in the proof of concept, and is reported as a limitation.
